<objective>
Build the panel pipeline: derive a shot size from each beat, compose a prompt that carries
the house style and the facial rule, generate one image per beat, and record every panel in
an index that says what it was drawn from and why.

Purpose: this is Phase 3's machinery run once per beat instead of once per slot. Nothing
here is a new architecture — the image call shape, the honest S3 write, the shared style
block and the "positive prose, rule last" discipline all already exist and were paid for
with real regeneration passes. The two genuinely new pieces are the close-up facial clause
(brow, mouth and nose shown while the eyes stay blank — no precedent in this codebase) and
a cache key that survives a slot's art being replaced.

Output: `panel_prompt.py`, `panel_generator.py`, `panel_manifest.py`, `scripts/build_panels.py`,
three test modules, and one real panel on disk and in S3 proving the whole path.
</objective>

  <action>
Give the pipeline the memory and the resilience a 49-call run needs.

**Cache key.** `panel_cache_key(beat, shot_size, dependent_slots, prompt_template_version)`
is a sha256 over a `sort_keys` JSON payload of the beat_id, the beat type, the beat content,
its sorted character names, its scene, the derived shot size, the sorted `(slot_id,
content_hash)` pairs for every slot the beat depends on, and the template version. Leave
`reason` and `duration_secs` out — neither changes the picture.

Each dependent slot's `content_hash` is read fresh from the current
`output/assets/manifest.json` at build time. Do not consume that manifest's `stale_beat_ids`:
it is computed once, at Phase-3-manifest-build time, relative to whatever the previous
manifest happened to be at that instant, and Phase 4 runs on its own schedule — a user can
regenerate slot art three times before Phase 4 next runs. Keeping Phase 4's own record of the
`(slot_id, content_hash)` pairs each panel was built from and diffing it against the current
manifest is the same content-hash-not-timestamp, re-runnable-not-order-dependent principle
`asset_manifest.py` already commits to in its own docstring. This is also what closes
Phase 3's ROADMAP criterion 4 — replacing a slot file and re-running redraws the panels that
use it — and what satisfies this phase's criterion 5.

`PROMPT_TEMPLATE_VERSION` is a constant in `panel_prompt.py`, bumped by hand whenever a
clause changes, and it is part of the key. Phase 3's history is the argument: the same beat
and the same slot art produced a passing and then a failing image purely because the subject
clause was reworded, and picking that up took a manual `--force`. With the version in the
key, a wording fix redraws on the next ordinary run.

**The loop.** `generate_missing_panels(beats, slots, manifest, previous_index, force, only,
on_progress)` mirrors `generate_missing_art`'s shape. For each beat in beat order: derive the
shot size, resolve the slots, build the prompt, compute the key. If the previous index has an
entry for that beat_id with the same key and its panel file is still on disk, reuse it and
record `source="reused"` with a reason naming why (and how to override). Otherwise call the
API.

Wrap each beat's call in try/except: one retry after a two-second sleep, then record
`source="generation_failed"` with `f"{type(e).__name__}: {e}"` in `source_reason` and
continue. One bad panel must not kill a 49-beat run — the same rule FR-02 applies to slots.
A single transient error costing one extra call is cheap against a nine-minute budget; a
retry framework is not worth a new dependency for five lines.

Write each panel's bytes local-then-S3 immediately after its own call succeeds, inside the
loop, exactly where `write_slot_art` sits inside `generate_missing_art`. Never accumulate and
flush at the end: a run interrupted at panel 40 would lose all 40.

**The whole-index rule.** `--scene` and `--only` narrow which beats are *generated*. Every
beat in the list still reaches `output/panels/index.json`, unselected ones carried through
from the previous index unchanged. Narrowing the collection instead of the generation is
precisely the bug that wrote a one-entry manifest over the full sixteen in Phase 3 and
orphaned the art behind it.

**Sequential, not concurrent.** Roughly ten seconds per image, so about nine minutes for a
full 49 (D-10), which is the budget this phase was scoped against. This model's real
per-minute limits could not be verified, so keep calls sequential; if concurrency is ever
added, keep it to a few workers with quota-aware backoff.

Tests go in `tests/test_panel_manifest.py` (index shape, reason fields, slot-hash
invalidation, mirroring `test_asset_manifest.py`'s `_detect_changes` tests) and extend
`tests/test_panel_generator.py` (reuse, retry, failure isolation, the whole-index rule).
